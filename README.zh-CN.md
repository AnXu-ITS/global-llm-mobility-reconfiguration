# 时限感知的地空服务重构运行时监督（Deadline-Aware Runtime Supervision for Ground–Air Service Reconfiguration）

面向 **HSCC + ICCPS 2027** 的研究代码与实验工作区。 · [English →](README.md)

> **一句话。** 当一个*慢*决策器（LLM）基于已经过时的观测提出服务重构，而交通、故障与服务截止时间仍在持续演化时，执行层应当如何避免把仍然有效的恢复机会，浪费在等待、过时提案、资源冲突和未完成的交接上？

本仓库实现了面向地空移动服务、叠加 SUMO（地面）+ BlueSky（空中）仿真的**时限与资源感知的异步运行时监督器**。LLM 被当作*可替换的慢提案器*，拟贡献在**执行机制**而非模型本身。

## 背景与动机

本项目的早期版本比较*哪种监督策略*（启发式 vs. LLM 提案）在地空系统受扰时重构得更好。后续工作转向一个更尖锐的问题：一旦慢提案器进入回路，**损失更多来自"执行器在提案计算期间做了什么"**——等待、应用过时提案、重复占用共享资源、或完成一个从未真正完成的交接——而较少来自"选哪个方案"。

因此不再要求 LLM"胜过启发式"，它保持为一个慢的、结构化的提案源；新颖性转向：

1. **带物理前置条件的异步服务执行模型** —— 请求 / 版本 / 操作 / 载荷状态全程可追溯；
2. **联合管理时间预算与资源 / 交接承诺的监督机制**；
3. **两级验证体系** —— 协议级（R1）加闭环物理级（R3/R4）证据。

## 研究问题

- **RQ1 · 执行一致性** —— 在重复、乱序、延迟、超时与多任务争用下，系统能否保持任务版本、资源归属与载荷阶段一致，且不无限拒绝或无限等待？
- **RQ2 · 机会保留** —— 相对调参后的固定超时与最晚启动规则，时间与资源的联合管理是否减少可避免的迟到？收益是否只出现在资源冲突 / 交接未就绪 / 相位敏感条件下？
- **RQ3 · 系统代价与范围** —— 在真实异步调用、显式地面 / 交接模型与更大有效载荷下，这些机制带来多少执行开销、资源闲置或原服务损失？

## 方法

只有一个仿真所有者能改动世界状态；提案工作进程读取不可变快照并返回结构化提案。

```
世界 / 故障 / 任务
        │
   快速监督器 ── 不可变快照 ──► 慢提案器（LLM）工作进程
        │                          │ 结构化提案
        ▼                          ▼
  接纳 · 版本与资源检查 · 有限期预留 · 下发 · 生效确认
        │
        ▼
   SUMO（地面）+ BlueSky（空中）+ 任务 / 载荷注册表
```

任务的等待预算由其当前可行回退方案的剩余裕量预测，

```
B_m(t) = d_m − t − T_fallback(m, t) − T_monitor+issue − ε
```

而非单一全局超时。四种执行器变体隔离机制：

| 变体 | 等待规则 | 跨阶段资源规划 |
|---|---|---|
| `X_FIX` | 开发集调参的固定超时 | 仅当前状态检查 |
| `X_LST` | 最晚启动 / 剩余时限规则 | 仅当前状态检查 |
| `X_TX` | 固定超时（同 `X_FIX`） | 预留 + 交接相位规划 |
| `X_FULL` | 动态时间预算 | 联合时间 + 资源 / 交接管理 |

主要预注册比较为 `X_FULL − X_LST`，在相同物理与信息权限下进行。

## 已实现内容

- **R0** —— 27/27 历史回放复现任务时长、动作表与完整动作流水线（仅排除 decision ID）。锚点：B0 D0/D30/D60 = 182/212/242 s，B1 = 342 s，B2 = 302 s。
- **R1** —— `runtime_v2/core.py` 实现操作去重、任务 / 资源版本、资源束原子占用、带端点的等待租约、不可后延的 due-time、取消语义、终态释放与载荷保管前置条件。8 族 × 6 个具名变体 = 48 用例；6 个故意破坏的变体全部被检出；720 条调度枚举（两任务争一资源，深度 6）未发现检查器违例。
- **最小物理闭环** —— 单载荷：装载 → 空中运输 → 故障 → 本地返航 → V3 交接 → 地面运输 → 卸载。交接要求载具、地面车与设施物理同时就位 30 s；送达使用 SUMO 真实到达事件 + 15 s 卸载，不用 ETA 计时器。三组设施等待对照（0 / 30 / 120 s）通过。
- **站点 D/E/F** —— 莱比锡、巴塞罗那、柏林由真实 OSM 导入，各自单载荷闭环诊断通过；正式场地验收待完成。

## 复现当前结果

确定性回放与协议检查从仓库根目录运行（Python 3、SUMO、BlueSky；精确环境记录在 `research_hscc2027/outputs/bootstrap/`）：

```powershell
python -B research_hscc2027/tools/run_r0.py              # 历史回放
python -B research_hscc2027/tools/run_r1.py              # 协议内核用例
python -B research_hscc2027/tools/run_physical_controls.py
python -B research_hscc2027/tools/plan_experiments.py --check
```

生成的 runs/outputs 不入 Git（见 `.gitignore`），靠外部备份 + 索引恢复；原始路网地图由 OSM 重新生成。
